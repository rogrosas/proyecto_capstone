Cómo se conecta la aplicación

El backend está organizado por capas y solo la capa de datos habla con PostgreSQL. Cada petición del CRM recorre este camino:

01 · public/
Navegador
crm.js llama a /api/crm/... con la cookie de sesión.
02 · presentacion/
Ruta y controlador
Valida la sesión y pasa los datos al servicio. No escribe SQL.
03 · negocio/
Servicio
Aplica reglas (quién puede qué, filtros válidos) y abre la transacción con conUsuario().
04 · datos/
Repositorio
Ejecuta el SQL con parámetros y convierte los tipos.
05 · EO_ER
PostgreSQL
Aplica RLS, CHECK, triggers y auditoría con la identidad del usuario.
Qué hace conUsuario() en cada transacción (src/datos/conexion.js): 
BEGIN;
SELECT set_config('app.usuario_actual', '<id del usuario>', true),
       set_config('app.rol_actual',     '<rol de la tabla roles>', true);
SET LOCAL ROLE rol_admin;        -- o rol_ejecutivo, según el rol
-- ... consultas del repositorio ...
COMMIT;                          -- ROLLBACK si algo falla

Así app_usuario() y app_es_admin() devuelven al usuario real: las políticas RLS filtran las filas, los GRANT limitan lo que puede hacer el rol, y los triggers de auditoría registran el autor de cada cambio. El inicio de sesión y el registro de LOGIN/LOGOUT usan la conexión directa (antes de conocer al usuario). Los errores de PostgreSQL se traducen a mensajes claros: 42501 sin permiso, 23503 registro con dependencias, 23505 duplicado, 23514 dato que no cumple una regla (p. ej. RUT inválido).

Seguridad y roles

La base de datos define dos roles de PostgreSQL. La app elige uno según el rol del usuario en la tabla roles: "admin" y "dueno" trabajan como rol_admin; cualquier otro, como rol_ejecutivo.
